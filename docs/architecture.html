Ork Architecture

This document describes the architecture of Ork, including design patterns, component relationships, and key architectural decisions.

System Overview

Ork is organized into a layered set of packages. User code interacts with the ork package, which exposes NodeInterface, GroupInterface, and InventoryInterface. These rely on the ssh package for connectivity and the types package for shared types and the skill system. Skill implementations live under skills/ (apt, user, swap, mariadb, security, ufw, fail2ban, ping, reboot, fs, php).

User Code └── ork Package ├── NodeInterface ──┬── ssh Package ── SSH Server ── Remote Server ├── GroupInterface │ └── InventoryInterface └── types Package ── skills/{apt,user,swap,mariadb,...}

Layered Architecture

1. API Layer (ork Package)

The public API that users interact with:

// NodeInterface - Single server management
type NodeInterface interface {
    RunnerInterface
    GetHost() string
    SetPort(port string) NodeInterface
    Connect() error
    Close() error
    // ...
}

// GroupInterface - Server group management
type GroupInterface interface {
    RunnerInterface
    GetName() string
    AddNode(node NodeInterface) GroupInterface
    // ...
}

// InventoryInterface - Multi-group management
type InventoryInterface interface {
    RunnerInterface
    AddGroup(group GroupInterface) InventoryInterface
    SetMaxConcurrency(max int) InventoryInterface
    // ...
}

2. Core Services Layer

SSH Package

Handles all SSH connectivity. Key features:

  • Connection pooling via persistent connections
  • Dry-run mode support
  • Key-based authentication

Types Package

Central configuration and type definitions:

type NodeConfig struct {
    SSHHost      string
    SSHPort      string
    SSHLogin     string
    SSHKey       string
    RootUser     string
    NonRootUser  string
    DBPort       string
    DBRootPassword string
    Args         map[string]string
    Logger       *slog.Logger
    IsDryRunMode bool
}

3. Skill System Layer

RunnableInterface (types package)

All automation tasks implement this interface:

type RunnableInterface interface {
    GetID() string
    GetDescription() string
    SetNodeConfig(cfg NodeConfig) RunnableInterface
    GetArg(key string) string
    SetArg(key, value string) RunnableInterface
    Check() (bool, error)
    Run() Result
    ToMap() map[string]any   // serialize state for cloning
    FromMap(m map[string]any) // restore state from a clone
    BecomeInterface
}

The ToMap()/FromMap() pair is the contract the framework uses to clone a runnable before mutating it during parallel execution (see Concurrency Model).

BasePlaybook & BaseSkill (types package)

Provide default implementation with fluent API. State is stored in an omni.AtomInterface (thread-safe) plus a mutex-guarded NodeConfig. Both implement ToMap()/FromMap() for the standard properties (id, description, args, dryRun, timeout, becomeUser, nodeConfig).

Design Patterns

1. Fluent Interface (Method Chaining)

Configuration uses fluent API for readability:

node := ork.NewNodeForHost("server.example.com").
    SetPort("2222").
    SetUser("deploy").
    SetKey("production.prv").
    SetArg("env", "production")

2. Repository Pattern (Registry)

Skill registry (types.Registry) for ID-based lookup. The global registry is a lazily-initialized singleton (ork.GetGlobalSkillRegistry()).

3. Strategy Pattern

Different skills implement the same RunnableInterface: apt.AptUpdate, user.UserCreate, swap.SwapCreate, mariadb.Install, security.SshHarden, etc.

4. Composite Pattern

Inventory / Group / Node hierarchy. All implement RunnerInterface with unified execution.

Inventory ├── Web Group │ ├── Node 1 │ └── Node 2 └── DB Group ├── Node 3 └── Node 4

5. Factory Pattern

Node creation methods:

func NewNodeForHost(host string) NodeInterface
func NewNode() NodeInterface
func NewNodeFromConfig(cfg types.NodeConfig) NodeInterface
func NewGroup(name string) GroupInterface
func NewInventory() InventoryInterface

Concurrency Model

Inventory-Level Concurrency

When Inventory.Run(skill) is called, all nodes are collected and the skill runs concurrently across them. Configurable via SetMaxConcurrency() (default: 10).

User ── Run(skill) ──> Inventory Inventory collects all nodes par concurrent execution: Node1.Run(skill) Node2.Run(skill) Node3.Run(skill) Inventory ──> User: aggregate Results

Skill Cloning (per-goroutine isolation)

When Inventory (or Group) runs a single shared skill instance across many nodes concurrently, the framework must not let goroutines mutate the same skill fields. To guarantee this, nodeImplementation clones the skill before setting any per-execution state on it:

User ──> Node: Run(skill) Node ──> Skill: skill.ToMap() Node: cloneFromMap(skill, map) reflect.New(typ) then clone.FromMap(map) function-typed fields (runFunc, checkFunc) are copied directly from the template Node ──> Clone: SetNodeConfig(node.cfg) Node ──> Clone: SetDryRun(node.IsDryRunMode) Node ──> Clone: SetBecomeUser (if empty) Clone ──> Clone: Run() Clone ──> Node: Result Node ──> User: Results

The clone is created via cloneFromMap(template, m) in node_implementation.go, which uses reflect.New to allocate a fresh value of the same concrete type as the template, calls FromMap(m) to restore serializable state, and then copies function-typed fields (runFunc, checkFunc, ...) directly from the template because they cannot survive a ToMap/FromMap round-trip.

Requirements for custom skill types:

  • Implement ToMap()/FromMap() to serialize any custom non-function fields. Fields that are neither serialized via ToMap/FromMap nor function-typed will be lost on clone. For example, commandImplementation overrides ToMap/FromMap to preserve command/required/chdir.
  • The embedded *BaseSkill / *BasePlaybook already implements ToMap()/FromMap() for the standard properties.

A race-detector test (race_detector_test.go) verifies that concurrent node.Run() calls sharing a single skill instance do not race.

Thread Safety

Key thread-safe mechanisms: Group uses a mutex for dry-run mode; BaseSkill and BasePlaybook store simple properties in an omni.AtomInterface (thread-safe via its own sync.RWMutex) and guard NodeConfig with a per-struct sync.RWMutex. Combined with per-call cloning, the original shared skill instance is never mutated during parallel execution.

Data Flow

Command Execution Flow

User ──> Node: RunCommand("uptime") Node checks IsDryRunMode if Dry Run: Node logs "would run command" Node returns [dry-run] marker else Normal Execution: if persistent connection: Node ──> SSH Client: Run(cmd) else: Node ──> SSH: Run(cfg, cmd) SSH ──> Remote: Execute command Remote ──> SSH: Return output SSH ──> Node: Return output Node ──> User: Return Results

Skill Execution Flow

User ──> Node: Run(skill) Node ──> Skill: skill.ToMap() Node: cloneFromMap(skill, map) Node ──> Clone: SetNodeConfig / SetDryRun / SetBecomeUser if Dry Run: Clone logs planned actions, returns [dry-run] Result else: Clone ──> SSH: Run(command) SSH ──> Remote: Execute Clone builds Result Clone ──> Node: Return Result Node wraps in Results ──> User

Idempotency Design

All skills follow the Check-Run pattern:

Skill Run └── Check? ├── Changes Needed ──> Execute Changes ──> Return Changed └── No Changes ──> Return Unchanged

Example implementation:

func (p *MySkill) Check() (bool, error) {
    // Check current state
    output, _ := ssh.Run(cfg, types.Command{Command: "check command"})
    return !isAlreadyConfigured(output), nil
}

func (p *MySkill) Run() Result {
    needsChange, _ := p.Check()
    if !needsChange {
        return Result{Changed: false, Message: "Already configured"}
    }

    // Apply changes
    _, err := ssh.Run(cfg, types.Command{Command: "apply command"})
    if err != nil {
        return Result{Changed: false, Error: err}
    }

    return Result{Changed: true, Message: "Changes applied"}
}

Error Handling Strategy

Result-based error handling. Errors bubble up with context:

type Result struct {
    Changed bool
    Message string
    Details map[string]string
    Error   error  // Non-nil if execution failed
}
output, err := ssh.Run(cfg, cmd)
if err != nil {
    return types.Result{
        Changed: false,
        Message: "Operation failed",
        Error:   fmt.Errorf("failed to execute '%s': %w", cmd, err),
    }
}

Security Architecture

SSH Security

  • Key-based authentication only
  • Private keys stored in ~/.ssh/
  • No password authentication in framework

Dry-Run Safety

Safety enforced at the execution layer - no way to bypass. SetDryRunMode propagates from Inventory → Group → Node → Skill.

Extension Points

type MySkill struct {
